# Implementation Plan: Electronic Scale Weight Capture

**Branch**: `008-electronic-scale` | **Date**: 2026-10-20 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/008-electronic-scale/spec.md`

## Summary

Add serial weight capture to the existing keyboard-input data source. The UI and document
model already carry the scale configuration (`inputDevice`, `weighProtocol`, `weighPort`,
`weighBaud`, `weighUnit`, `weighDecimals`, `weighAutoPrint`, `weighUnitConv`), but no read
logic exists. The feature adds a shared protocol/units layer, a main-process serial reader
using the already-installed `serialport` package, additive IPC channels for read/test/cancel,
per-label weight resolution before print/preview, and an auto-print loop driven by stable
readings. The print pipeline, `PrintPlan`, protocol builders and template format are not
changed; only the value injected into the existing keyboard data source changes.

## Technical Context

**Language/Version**: TypeScript 5.x, React 18, Electron 44.3.0, Node.js 22.12.0

**Primary Dependencies**: `serialport@13` (already a dependency, already unpacked by
electron-builder). No new runtime dependency. No i18n dependency; messages use the existing
shared catalog.

**Storage**: Existing template document fields on a keyboard data source
(`KeyboardSource`). Language, scale readings and diagnostics are not persisted; only the
configuration is saved with the template.

**Testing**: Vitest (unit/contracts/integration) and Playwright Electron E2E, following
`app/tests/`. Serial I/O is injected behind a `ScaleTransport` interface so tests use a
scripted fake port; E2E uses a simulation transport selected by a test-only environment
variable.

**Target Platform**: Windows 10/11 x64 primary (PowerShell is not required for reads);
`serialport` also supports macOS/Linux for `005-cross-platform`.

**Project Type**: Desktop application (Electron main/preload/renderer/shared).

**Performance Goals**: A stable read completes within the configured timeout (default
5000 ms); the UI stays responsive because all serial work runs in the main process; one
serial connection and one in-flight read at a time.

**Constraints**: Offline-capable; no second print executor; exactly one scale read per
logical label (preview uses one sample read and does not consume print readings); cancel
and timeout release the port; captured values are language-independent.

**Scale/Scope**: One active scale, 8 declared protocols (7 vendor/generic adapters plus a
documented custom fallback), 5 units (`g`, `kg`, `lb`, `oz`, `jin`), decimals 0–4. Real
device verification is manual and deferred because no device is available in this
environment; protocol frames are declarative and isolated so corrections are local.

**Structure Decision**: Shared parsing/units live in `shared/scale/` because both the main
process (read) and tests need identical semantics. The serial lifecycle stays in
`main/scale/` behind an injectable transport. React orchestration stays in
`renderer/features/scale/`. No new package or process.

## Phase 0 — Research

See [research.md](./research.md). Decisions:

- D-001: Declarative protocol registry + shared parser, not per-brand code branches.
- D-002: `serialport@13` behind a `ScaleTransport` interface; scripted fake for tests.
- D-003: Per-label values via `scaleValues` in the existing data-source context.
- D-004: Stability = stable flag plus the same value for two consecutive frames within the
  timeout; unit conversion factors are exact constants.
- D-005: Auto-print is a renderer loop: one stable reading → exactly one logical label
  (repeated by the copies-per-label setting) → next read. The print count is ignored while
  auto-print is active; the existing print executor is reused, with no second pipeline.
- D-006: `custom` protocol is a strictly validated tolerant parser that extracts a signed
  decimal and a known unit; an ambiguous frame fails with `error.scaleCustom` and is never
  partially parsed. No user-supplied pattern field is added in v1.
- D-007: No real device: representative frames are documented assumptions in
  `contracts/scale-protocols.md`; adapters are isolated for correction. The eight presets
  ship as normally supported protocols with no experimental warning; per-model frame
  verification is a deferred manual item tracked as `TODO(device)`.
- D-008: `weighUnit` is the label output target: conversion is applied when
  `weighUnitConv` is enabled, and the scale-reported unit is kept when it is disabled.
- D-009: A preview performs one separate sample read and does not consume the readings
  reserved for printing; printing reads a fresh stable value per logical label.

## Complexity Tracking

| Change | Why Needed | Simpler Alternative Rejected Because |
|--------|------------|--------------------------------------|
| Add `scaleValues` to the data-source context | FR-007 requires a fresh stable reading per logical label, while `keyboardValues` holds one value per label name | Reusing `keyboardValues` would print the same weight on every label |
| New additive `scale:*` IPC channels | Serial I/O must stay in the main process | Renderer serial access is blocked by the sandbox/preload boundary |
| Auto-print loop in the renderer | FR-006 requires printing after a stable reading without a separate manual action | Doing it in main would duplicate print orchestration and bypass the existing executor |
